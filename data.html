Data Requirements#

General Transit Feed Specification (GTFS)#

RouteE-Transit relies on input data in the static GTFS format to generate energy predictions for each trip. Some features, such as complete shape traces for each trip, are optional per the GTFS standard but mandatory for RouteE-Transit analysis. In addition to all files and columns required by the GTFS standard, RouteE-Transit requires the following GTFS tables and fields:

  • trips.txt: trip_id and shape_id for all trips

  • shapes.txt: complete shape traces (shape_pt_lat, shape_pt_lon, shape_pt_sequence) for each trip

  • stop_times.txt: all stop time data for each trip_id included

  • stops.txt: stop coordinates for any stop served on any trip to be analyzed

Elevation Data#

Road grade is computed automatically by RouteE-Compass using OSMnx to fetch elevation data from the USGS National Map. No manual download or configuration is required. For large geographic areas, the initial OSMnx network download may take additional time, but results are cached for subsequent runs.

Transit Speed Model#

RouteE-Transit predicts the average moving speed of a transit bus on every OpenStreetMap road link with a machine-learning model trained on archived GTFS Realtime (GTFS-RT) vehicle positions. These speeds replace OSM posted speeds for map matching, deadhead routing, travel time, and energy prediction. The model is bundled with the package (routee/transit/resources/speed_models/random-forest/), so no realtime data is needed to run predictions.

The model is a single pooled random forest intended to generalize to agencies it has never seen. It uses only features available for any U.S. road network plus a static GTFS feed. It is a proof of concept: see accuracy and limitations below.

Inputs and time bins#

Each link gets 12 speeds: six local-time periods for weekdays, followed by the same six for weekends.

Boundaries belong to the period starting at that time. The model has 24 inputs:

  • Road attributes from OSM: posted speed (mph), lane count, link length (km), signed and absolute grade, and FHWA-style functional class derived from the OSM highway tag (freeway, principal arterial, minor arterial, collector, local; one-hot encoded).

  • Transit context: number of GTFS stops nearest to the link.

  • Time: six period indicators and a weekday/weekend indicator.

  • Missing-value flags: one per numeric road attribute. Missing values are imputed with training-set medians stored in the model manifest.

Scheduled GTFS speed, agency identity, route identity, and road identity are deliberately not inputs. Scheduled speed is unavailable on arbitrary network links, and the identifiers would not generalize to new agencies.

How speeds are used at runtime#

During Compass dataset generation, RouteE-Transit runs the ONNX speed model over all road links in bounded batches. Predictions are floored at 1 mph; invalid model outputs stop preprocessing. Speeds are rounded to 0.1 mph, then identical 12-value traces share a trace ID. The cache stores a dense little-endian uint32 edge-to-trace mapping in transit_speed_edge_traces.bin and consecutive 12-value little-endian float32 mph traces in transit_speed_traces.bin. Storage is 4 bytes per edge plus 48 bytes per unique trace, excluding file metadata.

A single Compass application shares these immutable tables across queries. Map matching, deadhead routing, elapsed travel time, and energy calculations all use the same lookup speed (edge_speed, also exposed as transit_speed). edge_speed is in km/h and transit_speed is in mph. The lookup selects the bin at entry to each edge using departure time plus accumulated travel time, including turn delays. Hours and weekdays roll forward across midnight, including GTFS departures beyond 24:00:00. Speeds are constant within each period and are not interpolated within an edge. A* estimates use the maximum trace speed, subject to a query's speed limit.

Energy queries are not expanded across service dates: path calculation runs once per matched shape and vehicle model. Trips sharing a shape use its earliest departure. Without a date filter, the representative service day defaults to Monday. Calendar expansion and HVAC modeling happen afterward. Energy estimates are therefore representative per shape, not trip-specific by departure time.

ONNX Runtime is a runtime dependency because it runs during preprocessing. Rust traversal does not use it. Cached datasets are reused when output_dir is provided and overwrite=False. Datasets with an old speed configuration, missing trace files, or changed model/manifest files are rebuilt automatically. Adding vehicle models to an otherwise valid cache preserves the traces without repeating inference. To use a different trained model, pass speed_model_dir to GTFSEnergyPredictor.

Estimating link speeds from GTFS-RT#

scripts/gtfs_realtime/archive_speeds.py estimates one speed per trip and road link from each trip's vehicle positions, using the shared library in realtime_speeds.py:

  1. Pair realtime with schedules. Download vehicle positions for a day and join them to the matching static GTFS trips.txt. Days where fewer than 50% of realtime trip IDs match the static feed are skipped.

  2. Clean each trip's trace. Drop duplicate reports and sort chronologically.

  3. Map match. Match the trip's GPS trace to the OSM network with RouteE-Compass. Assign each GPS point to a matched edge, and project it onto the route to get cumulative distance. Distance is forced to be non-decreasing because the bus only moves forward along its route.

  4. Interpolate link traversal times. Linearly interpolate timestamps at each link boundary from cumulative distance. Travel time on a link is exit time minus entry time.

  5. Remove dwell time. Consecutive points on the same link less than 10 m apart and more than 15 s apart count as dwelling. Moving speed is link length divided by (travel time − dwell time).

  6. Attach features. Record OSM attributes, grade, and the number of GTFS stops projected onto the link. Links with at least two GPS points are labeled observed; others are interpolated.

Output is one row per trip and link, partitioned as link_observations/agency=<slug>/date=<YYYY-MM-DD>/.

Model training#

scripts/gtfs_realtime/fit_poc_speed_model.py trains the bundled model:

  1. Filter observations. Keep only observed links with a finite moving speed between 1 and 65 mph. Remove outliers outside 1.5 × IQR per road link (for links with at least four observations).

  2. Assign local time bins. Convert archive timestamps, which are naive UTC, to each agency's local time zone, then assign period and weekday/weekend from the link entry time.

  3. Aggregate. Group by road link, period, and day type. The target is the GPS-point-weighted mean moving speed (mph_moving_mean). Keep groups with at least three trip-link observations.

  4. Weight agencies equally. Sample weights are point-weighted within each agency and normalized so each agency has equal total influence.

  5. Fit. Train a RandomForestRegressor with 100 trees, maximum depth 8, minimum leaf size 10, max_features=0.5, and random_state=42. There is no hyperparameter search.

  6. Evaluate, then refit. Evaluate with three agency-grouped folds, learning imputation medians from training agencies only. Then refit the final model on all nine agencies.

  7. Export. Export to ONNX with skl2onnx, validate against scikit-learn predictions, and write a JSON manifest. The manifest records input order, medians, the functional class mapping, time bin boundaries, and training metadata.

See the training instructions for commands.

Limitations#

  • Small, regional sample. Nine mostly small and mid-sized agencies, five of them in the Eastern time zone, over three sampled weeks each. Large, congested systems and rail-like bus operations are underrepresented.

  • Link length dominates. Short links tend to have lower measured speeds, partly because of acceleration and deceleration near intersections and stops. Some of the effect may also come from how GPS points are assigned to links and boundary times are interpolated.

  • Weak temporal signal. Peak and off-peak speeds are nearly identical in predictions.

  • Moving speed only. Dwell time at stops is excluded from the target.

  • Training/inference differences. Training stop counts come from stops projected onto each trip's matched route. At inference, every GTFS stop is assigned to its nearest network edge. The model is trained only on links that buses traversed but is applied to every link, including those used only by deadhead routing.

  • Representative departure time. As described above, each shape uses one representative departure time rather than each trip's own time.
